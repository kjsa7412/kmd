## §0 결론 — 충분한가

노트는 CDP 의 조회(match · search · where · section) · 미반영 · 쓰기 · 큐레이션 · 기준선 · drift · 정정 · 들이기를 대체로 정확하게 잡았다. 미반영 계산식은 CDP 설계서(§3.6)와 용어집보다 오히려 코드에 더 맞고, 노트가 추정만 했던 「MCP 호출마다 레포를 다시 읽는다」 는 코드와 실측으로 맞음을 확인했다.

**틀린 것은 둘이다.** ① 미반영 상한(8건 · 3만 자)에서 빠지는 것은 오래된 기록이 아니라 **가장 새 기록**이다(섹션이 있는 좌표 · 코드와 실험이 같은 결과). ② 「문서가 10배가 돼도 **조회 비용은 거의 그대로**」 는 설계(좌표로 바로 감)로는 맞지만 지금 구현은 반대다 — 요청마다 레포 전체를 다시 읽고 search 는 색인과 섹션 훑기를 다시 해서 조회 비용이 레포 크기에 비례한다. 노트 자신의 7-1 「약 1,000건」 행과도 어긋난다(§1.0).

**어긋남 14건**은 대개 세부 규칙의 모양이다 — 시각 비교, search 의 「상위 20 기록」 · 「질의 낱말의 70%」, match 실패 때의 「비슷한 문서」, 들이기 도구 목록의 「만」 · 「사람이 체크한 좌표만」, save 순서, 정정의 역방향, 「레포별 토큰」. **줄임 34건**은 요약표에서 줄인 것이다(맞게 쓰고 일부를 뺐다). 누가 지키나를 가르지 않은 문장도 몇 있다 — 현재형 · 경과 한 줄과 keep 사유는 스킬 · MCP 명함이 내보내는 규칙이고 서버는 검증하지 않으며(keep 사유는 화면 [기록으로 둠] 에서만 서버가 요구한다), 「기계만 쓰는 칸」 은 신원이 아니라 save 입력 칸으로 지킨다. 사람 승인과 dryRun 의 diff 는 여기에 들지 않는다 — 노트는 diff 를 세션이 만든다고 썼고(노트 :115 · :231), 승인은 서버가 강제하지 않는다고 스스로 적었다(노트 :630).

그러나 **kmd 의 바탕으로 쓰기에는 충분하지 않다.** 빠진 것이 세 무리다.
1. **팀 서버 모드와 계정 · 로그인** — 로그인이 토큰 붙여넣기이고 아이디 · 비밀번호가 없다는 사실(R3 · SaaS 의 바탕).
2. **불변조건 I1 · I9 · I12 · I13, I11 의 「깨지면」 칸(키 · 비용 · 반출), 요청마다 다시 읽는 까닭(캐시 배선)** — R4 의 RAG 폴백 색인을 어디에 어떻게 둘지 정하는 조건.
3. **자동화를 막는 실제 장치** — save 한 번으로는 자기 반영이 안 됨, 섹션 잠금은 applied 만 봄, 트리가 더러우면 save 거절, writer 의 프런트매터 주입(P0 — curates · baseline · snapshot), 사람 승인 게이트가 걸린 네 자리(스킬 · MCP 명함 · kit CLAUDE 블록 · 화면), 큐레이션 자동화에 없는 장치(R5 의 대상).

노트가 이 가운데 몇을 다른 말로 건드린 곳은 §2 에 노트 줄과 함께 적었다. 그래서 노트는 「CDP 가 무엇을 하나」 의 설명으로는 그대로 쓰고, kmd 설계의 근거로 쓸 때는 §1 의 바른 말과 §2 의 누락을 함께 써야 한다.

**셈** — 대조한 노트 문장 192건(여러 갈래가 본 같은 주장은 하나로 셈) = **사실 주장 184 + 제안 8**.
- **사실 주장 184** — **맞음 123 · 줄임 34 · 어긋남 14 · 틀림 2 · 추정 1 · 확인 못 함 10.** 추정 1 은 노트가 스스로 「이유로 보인다」 고 밝힌 보안 문장이다. 확인 못 한 10건은 모두 ezipez_cdp · 이집이지 쪽 숫자와 사례다(§4).
- **제안 8**(§1.13 · §1.14 의 「제안」 표) — **바로 가능 3 · 선결 있음 5.** CDP 에 대한 사실 주장이 아니라서 맞고 틀림을 매기지 않았다.

## §1 장마다 대조

판정 — **틀림**(코드와 반대) · **어긋남**(노트 문장의 일부가 코드 · 문서와 다르다) · **줄임**(쓴 것은 맞고 빠진 것이 있다 — 요약표라 생긴 것) · **맞음**(덧붙임은 kmd 에 쓸 사실) · **추정**(노트가 스스로 추정이라 밝힌 것) · **확인 못 함**. 노트의 **제안**은 사실 주장이 아니라서 §1.13 · §1.14 에 따로 표를 두고 「바로 가능」(지금 장치 위에 얹으면 된다) · 「선결 있음」(먼저 고치거나 지을 것이 있다)으로만 적는다. 각 표 안에서 틀림 · 어긋남 · 줄임을 위에 둔다.

### §1.0 틀린 둘 (먼저 읽을 것)

#### 첫째 — 미반영 상한에서 빠지는 것

> 노트 7-1 장 「약 100건」 행(노트 :425): *「섹션마다 붙는 미반영이 늘어 section 의 상한(미반영 8건 · 3만 자)에 걸리면 오래된 것부터 빠진다(pendingOmitted)」*
>
> **반대다.** 섹션이 있는 좌표의 미반영 목록은 오래된 순으로 정렬되고(`core/curation.js:291`), 본문은 그 앞 8건만 싣고 3만 자 예산도 앞(오래된 것)부터 쓴다(`core/tools.js:146-159`). 그래서 가장 새 기록이 먼저 빠진다. 8건을 넘는 새 기록은 id 만 남고(pendingOmitted 로 셈 · `tools.js:309`), 오래된 기록이 3만 자를 먼저 써 버려서 8건 안에 든 새 기록도 본문이 잘리거나 0자가 된다. 이 건은 pendingOmitted 에 세지 않는다 — 다만 그 기록에도 `truncated: true` 가 붙고(본문이 0자여도 · `tools.js:156`), 글로 낼 때는 「(…잘림 — work 로 전문)」 이 찍혀(`:291`) 흔적은 남는다. 실험 `exp-omit.mjs`(11건 · 건마다 5천 자): 오래된 5건 전문 · 6번째 잘림 · 7~8번째 본문 0자 · 9~11번째 빠짐(pendingOmitted 3). `exp-omit2\mk-synth.mjs`(12건)도 같은 모양(pendingOmitted 4). CDP 자신의 설계 의도(`docs/design/개념정리_RAG와좌표.md:284` 「최신 5건 주입」 · 절단은 흔적을 남긴다)와도 반대다.
>
> **예외 하나 — 두 경로의 순서가 다르다.** 섹션이 없는 좌표(등록부 없음 · 문서나 섹션 없음)는 미반영을 loose 경로(`tools.js:303-304`)로 모으는데, 이 경로는 byCoord 의 순서(`core/validity.js:41` cmpDateDesc · 최신순)를 그대로 쓴다. 그래서 거기서는 오래된 것부터 빠진다 — 노트의 문장이 맞는 경우가 하나 있는 셈이다. 이 경로는 암묵 전환 레포에 한하지 않는다: 큐레이션 기록이 있는 레포에서 등록부 없는 좌표에 기록 10건을 대기시키자 실린 8건이 최신 8건이었다(실험 `exp-critic\loose-order.mjs` · implicit false · pendingOmitted 2). 노트의 문장은 「섹션마다 붙는 미반영」 을 말하므로 판정은 틀림 그대로다.
>
> 미반영이 쌓일수록 「지금」 에 가장 가까운 결정이 먼저 안 보이고, 두 경로가 반대 순서라 같은 기록 묶음이 좌표의 처지에 따라 다르게 잘린다 — kmd 에서 고칠 거리다(§3.2).

#### 둘째 — 「문서가 10배가 돼도 조회 비용은 거의 그대로」

> 노트 7-1 장 운영 표 「문서가 10배가 되면」 행(노트 :452): *「큐레이션 노동이 늘어난다. 조회 비용은 거의 그대로(좌표로 바로 감)」*
>
> **설계로는 맞지만 지금 구현은 반대다.** MCP 요청마다 서버를 새로 짓고 레포 캐시(makeRepoCache)도 새로 만들어 레포 전체를 다시 읽는다(`viewer/bin/ctx-mcp-serve.mjs:677-755` · `viewer/bin/ctx-mcp.mjs:163-168`). search 는 그 위에서 색인을 다시 짓고 좌표마다 섹션을 다시 쪼개 훑는다(`core/tools.js:394` · `:409-420`). 그래서 match · section 처럼 「좌표로 바로 가는」 조회도 비용이 레포 크기에 비례한다. 실측(gdi 사본): 새 요청마다 0.5~1초 · readFile 130회(실험 `exp-a\percall` · `exp-tools\exp2`), loadRepo 0.32~0.45초 · buildIndex 0.36초(`exp-omit2\mcp-reload`). 노트 자신도 7-1 「약 1,000건」 행(노트 :427)에서 「코드상 MCP 호출마다 레포를 다시 읽고 … 캐시 · 영속 색인이 필요하다」 고 적어 이 행과 어긋난다.
>
> 좌표 직행이 싸다는 설계 의도(설계서:506 · `docs/design/CDP_MCP_설계서_v2.0.md:177-189` 의 HEAD 캐시)는 요청 밖에 사는 캐시가 있어야 성립한다 — kmd 엔진의 불변으로 적을 것(§2-7 · §3.2).

## §2 누락 — 노트가 다루지 않았거나 일부만 다룬 CDP 기능 · 개념 (kmd 중요도 순)

한 줄에 하나. 노트가 다른 말로 일부 다룬 항목은 앞에 「노트가 일부 다룸(노트 :줄) — 빠진 것:」 을 달고 빠진 부분만 남겼다. 「→」 뒤가 kmd 에 왜 중요한가(관련 요구).

### 높음

1. **팀 서버 모드** — `ctx serve --root <폴더> --auth auth.json`(기본 7374) · root 아래 레포 여럿을 60초마다 다시 훑음 · 명부 · 첫 관리자 `/setup` · 세션 쿠키 12시간 · 관리 재인증 15분 · 콘솔 · 미러 · Origin 검사 · IP 당 분당 20회 · 인증 없이 루프백 밖에 열면 시작 거부(설계서 §7 :426-518 · `ctx-mcp-serve.mjs:125-181` · `:533` · `:544-590`) → kmd 의 팀 서버(SaaS)는 이 모드가 바탕이고, R3(아이디 · 비밀번호)을 얹을 자리도 여기다.
2. **로그인 = 토큰 붙여넣기 · 아이디 · 비밀번호 없음** — 사람이 토큰을 다루는 자리가 다섯(브라우저 로그인 · 관리 재인증 · 설치 한 줄의 숨김 입력 · `ctx login` · 작업 레포의 CDP_TOKEN). 토큰 하나가 브라우저 신원과 MCP 자격을 겸하고, 비밀번호 · OAuth 는 「이 규모에서는 범위 밖」 으로 정해 두었다(`viewer/src/site/Login.jsx:1-5` · `ctx-mcp-serve.mjs:939-993` · `:1130-1148` · `viewer/bin/cdp-install.mjs:710-769` · `docs/design/CDP_관리서비스_사용자관리_검토_v0.1.md:153` · `:284`) → R3 의 직접 대상. kmd v0.5 KM53 은 이 방식을 그대로 이어받았다(kmd:CDP_kmd_개정_v0.5_검토.md:245 · :336).
3. **토큰 보관(tokenstore)** — Claude Code 는 `.mcp.json` 의 `${CDP_TOKEN}` 을 프로세스 환경변수로만 채운다. 그래서 Windows 는 setx, POSIX 는 파일 + rc 한 줄에 둔다(`core/tokenstore.js:1-20` · `:34-90`) → 사람 로그인을 비밀번호로 바꿔도 MCP 키는 남는다. 이 자리에 사람 대신 키를 저절로 넣는 길이 R3 · R5 의 핵심이다.

9. **match 의 exact:false 는 약한 신호인데 알리지 않는다** — 노트가 일부 다룸(노트 :46 엉뚱한 좌표라는 현상) — 빠진 것: 원인과 표시 — 한 방향 포함 대조라 짧은 alias 가 질의 안에 있으면 엉뚱한 좌표가 나오고, 질의보다 긴 alias 를 가진 진짜 대상은 놓친다. 명함 · cdp-work 표는 exact 칸의 뜻을 말하지 않는다(`core/vocab.js:200-207` · `ctx-mcp.mjs:38` · 실험 `exp-tools\exp1` · `exp3`) → 폴백 발동 조건을 「미등재 또는 exact:false」 로 잡아야 한다.
10. **화면 찾기의 이름 대조와 「본문까지 갔다」 표시** — 화면 Store.search 는 좌표 · 값 · alias · 설명마다 matchName(같음 100 · 앞 80 · 안 60 · 낱말 40)을 쓰고, 안 걸리면 BM25 본문으로 가며, 응답의 fullTextRan 이 「믿을 정도가 다르다」 를 알린다(`core/search.js:173-211` · `core/store.js:655-805` · 실험 `exp3`: '예산마스터' · '결의서작성자' 를 찾음) → 임베딩 없이 바로 쓰는 싼 1차 폴백이고, 「뜻으로 찾았다」 표시를 같은 꼴로 붙일 자리다.
11. **레포 가로지르기는 「섞지 않는다」** — 레포를 가로지르는 것은 match 하나뿐이고, 한 레포에서 못 찾은 이름을 미등재로 못박지 않으며, 한 답에 두 레포를 섞지 않는다(`ctx-mcp.mjs:51-52` · `:285-339`) → 폴백 색인도 지식마다 따로 · 권한(allow) 안에서 · 한 답에 섞지 않는다.
12. **미등재 이름이 서버에 남지 않는다** — 요청 로그의 peek 은 search 를 words:n 으로만 적고 match 의 이름은 적지 않는다. 화면 어휘 탭의 「미등재」 는 질의 실패가 아니라 기록이 쓴 미등재 좌표다(`ctx-mcp-serve.mjs:427-440` · `viewer/src/components/admin/VocabView.jsx:1-5`) → 못 찾은 이름 장부(지식별 집계 · `<data>`)가 있어야 alias 자동 제안과 폴백 품질 측정이 된다.

## §3 노트의 판단 — kmd 에 그대로 가져올 것 · 고쳐 가져올 것

### §3.1 그대로 가져올 것

1. **큰 틀** — 「CDP 는 쓰는 쪽(형식 · 이력 · 정본), RAG 는 찾는 쪽」 과 「이름이 어휘에 있으면 좌표, 없으면 뜻」. kmd 에서 좌표가 기본 길이고 폴백은 보조 길이다.
2. **미반영 계산식(4장)** — 코드와 같다. kmd 문서는 CDP 설계서 §3.6 대신 이 식을 옮긴다.
3. **「A · CDP 를 쓰기 창구로」** — 쓰는 길은 하나, 색인은 그 결과를 따라 증분한다. CDP 가 강제하는 id · 날짜 · 작성자 · touches · supersedes 를 폴백 색인의 조각 메타데이터로 쓴다.
4. **「대화 원문은 넣지 않는다」** — 결과를 정리한 기록만 색인한다.
5. **RAG 가 CDP 에서 배울 것 넷**(미반영 · 정본 하나 · 좌표 메타 · 판정 → 평가셋) — kmd 폴백 색인의 조각 규칙으로 쓴다.
6. **측정 방법** — 같은 문항으로 「찾아야 할 섹션을 찾았나」 를 재는 회귀 시험. kmd 폴백의 품질 측정과 자동 큐레이션의 사후 점검에 쓴다.
7. **제안 1 의 세 필요**(원천 · 뽑는 규칙 · 주기와 대상)와 「뽑는 규칙은 결정적 코드」(I11).
8. **제안 2 의 「사람 필수」 범주**(값 · 규칙이 바뀌는 반영 · 기록끼리 어긋남 · new · rename · retire) — 「자동이 기본」 이어도 이 범주는 화면에 결정 한 줄로 남긴다.
9. **「승인은 서버가 아니라 스킬이 강제한다」 는 관찰** — 맞다(서버는 강제하지 않는다). 다만 승인 문구는 스킬만이 아니라 서버가 내보내는 MCP 명함(save · saveCurator — `ctx-mcp.mjs:62` · `:64`)과 kit CLAUDE 블록 둘(`agent/CLAUDE-프로젝트레포.md:29` · `agent/CLAUDE-큐레이터.md:26`)에도 있다(§2-20). 그래서 kmd 의 자동화 안전장치는 세션이 아니라 엔진 쪽 정책으로 옮기고, 그때 **스킬 · 명함 · CLAUDE 블록을 같이 바꿔야 한다** — 자동 신원에게는 승인 문구 없는 도구 묶음 · 명함을 주고, 사람 세션의 명함은 지금처럼 둔다.
