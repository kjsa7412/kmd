## 진행 규칙

- 단계마다: 구현 → 바뀐 것에 걸린 테스트만(`npm test` 전체 · restore 테스트 · stash 금지) → 화면이면 네 폭(1280 · 1024 · 600 · 375) 잘림 0 → 기준 문서를 같은 커밋에서 → main 에 커밋 → 이 표에 커밋 해시.
- 검토(2026-11-10 사람 「너무 느리다 · 검토와 테스트 비중을 줄여라」): 단계마다 반박 검토는 하지 않고 **묶음 끝에 한 번**(아래 표의 「묶음」 칸이 바뀌는 곳). 권한 · 저장 문을 바꾸는 단계(P2 · P3 · PC1 · P6 · P7 · PC4 · P8 · PC5 · P11 · PC6)는 그 단계에서 바로 검토. 화면 테스트는 바뀐 화면만 `--test-name-pattern`, screen-kmd 전체는 묶음 끝에 한 번.
- 저장 승인 설계 7절의 규칙을 따른다: P1 ~ P2 는 **더하기만**. P3 부터는 approve 모드 지식(새 지식 포함)에서만 동작이 바뀌고 **held 모드 지식은 P11 까지 지금 그대로**. 짝인 팀 단계와 PC 단계는 같은 core 를 고치므로 그 core 커밋에서 PC 시험도 같이 돌린다(P-D26). 기준 문서의 「(Px 부터)」 줄은 그 단계 커밋에서 코드와 맞춘다(CLAUDE.md).
- 서로 다른 파일을 고치는 단계는 나란히 돌려도 된다(같은 파일을 두 일이 동시에 고치지 않는다 · `git add` 는 제 파일만).
- 커밋은 이 일의 파일만(다른 세션의 site/ · 그래프 목업 · `docs/kmd_vs_Obsidian.html` 등은 건드리지 않는다).
- push · 188 배포는 사람이 하라고 할 때만(배포 단계 P9 직전에 묻는다).
- 팀 지식에 남기는 시험 데이터는 「테스트」 · `test-`. 지우기는 사람이 확인한 뒤.
- 한도에 걸리면 기다렸다 잇는다. 막히면 「막힌 것」 에 적고 다음 단계로 가지 않는다.
