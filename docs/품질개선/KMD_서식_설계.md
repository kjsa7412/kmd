# 서식 설계: 기록 · 항목 · 문서를 짓는 서식 계약

> v1.1 · 2026-11-12 · 상태: 개발(사람 결정 8 은 권장안으로 확정 · 작성기준 6-3 으로 옮김)
>
> 같이 보는 것: 비교 보고서 [서식설계_비교.html](서식설계_비교.html)(안 넷을 실제 문서에 적용한 결과를 나란히) · 지금 기준 [작성기준](../kmd_문서_작성기준.md) · [템플릿](../템플릿/)

## 1. 결론

- **서식 계약 하나를 모든 길이 같이 쓴다.** 종류(대상 · 서술 · 사건 · 대장 · 결정 · 기록)마다 계약 하나(물음 · 머리 꼴 · 첫 문장 · 속성 · 라벨 차례 · 깊이)를 `core/forms.js` 의 데이터 한 벌(`FORMS`)로 둔다. 템플릿 글 · Claude 프롬프트 블록 · 기계 검사가 모두 이 데이터에서 나온다. 사람 편집 · 세션 저장 · 들이기 · 바탕 세우기 · 다듬기가 같은 계약을 본다.
- **안 A 「작성기준 확장」 을 골랐다.** 지금 작성기준 · 템플릿 · 종류 넷을 그대로 두고 계약만 더하는 안이다. 실제 긴 문서 표본 일곱에 안 넷을 적용해 견줬고, 표본 다섯에서 A 가 가장 좋았다(합 30 · C 29 · B 20 · D 20).
- **접붙인 것:** C 의 「서식 데이터 한 벌 · 옛 머리 `값:` 지키기」, B 의 「원본 칸 정의 표 · 「〃」 금지」, D 의 「검사 세 급 · 갈래별 찾으러 오는 물음」.
- **막지 않는다.** 막는 검사는 지금 `E_FORMAT` 다섯뿐이다. 새 검사는 짓기 길에서 「고쳐 받기」(같은 세션에 돌려보냄), 그 밖에서는 짜임 알림이다. 1단계는 확정 검사 열넷만 켠다.
- **옛 것은 건드리지 않는다.** 옛 항목은 사람이 「짜임 맞추기」 를 고를 때만, 옛 기록(`held` · `memo` · `migrate-held`)은 어떤 길에서도 다시 쓰지 않는다(P12).

## 2. 왜

실제로 kmd 가 원본 재료 94개로 지은 지식(로컬 「테스트」 · 문서 24)을 검토했다(2026-11-12).

| 증상 | 예 | 원인 |
|---|---|---|
| 요약 없음 | 24 문서 모두 `# 제목` 바로 아래 `##` | 짓기가 항목 글만 짓는다. 문서 머리말 단계가 없다 |
| 템플릿을 안 따름 | 회의 메타(일시 · 장소 · 참석)가 한 문단 · 정한 것과 할 일이 안 갈림 | 템플릿이 프롬프트 · 검사에 연결되지 않는다 |
| 대장 행 빠짐 | 원본 IS01 · IS02 → 문서는 IS01 + 「이슈 관리 필드 구조」(양식 설명) | 대장 계약 · 행 덮임 검사가 없다 |
| 값 변환 | 발생일 `44785`(엑셀 일련번호) | 원본 전처리가 날짜 칸을 바꾸지 않는다 |
| 번호 되풀이 | `1. 식별` · `1. 해결방안 수립` · `1. 해결` | 5-1 검사가 번호 차례를 보지 않는다 |
| 한 사실 여러 곳 | IS1 이 회의록 · 주간보고 · 대장에 따로 · 링크 없음 | 정본 · 링크 규칙이 짓기에 없다 |
| 표 칸에 목록 | 코드 표 한 칸에 코드값 10여 개를 「·」 로 | 표 · 목록 고르기 기준이 없다 |

## 3. 어떻게 정했나(실험)

1. **표본**: 실제 긴 문서 18. 원본 재료 6(회의록 · 위험및이슈관리대장 · 코드정의서 · 주간업무보고 · 통합테스트계획서 · 화면설계서) · kmd 가 지은 문서 6 · 사람과 세션이 다듬은 DPMS 팀 지식 4(대장 · 회의록 · 게이트웨이운영설계서 · 코드정의서) · 기록 2.
2. **레퍼런스 조사 둘**: 문서 갈래 · 정보 유형(Diátaxis · DITA · Information Mapping · Good Docs · arc42 · Google · Microsoft 문체) · 기록 · 대장 · 사건(ADR · MADR · 회의록 · RAID · Keep a Changelog · BLUF · Pyramid · plain language · markdownlint · Vale). 42곳을 직접 열었다(9절).
3. **안 넷이 같은 표본 일곱에 적용**: 회의(사건) · 이슈대장(대장) · 코드정의(대상 · 참조) · 주간보고(정례 사건) · 통합테스트계획(절차 · 표) · 게이트웨이운영설계서(사람이 쓴 설계서 다시 짜기) · 기록. 원본 값을 빠뜨리지도 지어내지도 않는다는 조건.
   - A 작성기준 확장: 지금 꼴을 지키고 갈래마다 계약만 더함
   - B 정보 유형: 항목마다 개념 · 절차 · 구조 · 사실 · 결정 · 사건 · 대장 행 유형
   - C 블록 스키마: 속성 블록 + 고정 덩이 · 기계 검사 우선
   - D 읽기 우선: 결론 먼저(BLUF · Pyramid · Diátaxis)
4. **반박 둘**: 원본과 대 보며 값 잃음 · 지어냄 · kmd 규칙 어김 · 긴 문서 붕괴 · Claude 가 지키기 어려움 · 다른 길에서 깨짐을 찾음 → 54건(막음 4 · 큼 37).
5. **심사**: 기준 여덟 점수 · 표본별 고르기 · 접붙이기 → 최종 초안(4 ~ 8절).

## 4. 서식 계약(작성기준 6-3 으로 옮겼다 · 작성기준 7절은 「경로마다 지키는 법」 이 쓴다)

안 A 를 바탕으로 C · B · D 를 접붙이고, 반박의 막음 · 큼 을 고친 심사 초안이다. 5절의 권장을 받으면 작성기준 7절로 그대로 옮긴다.

### 4-0. 범위와 힘

- 그대로 둔다: 작성기준 3 · 4 · 5 · 5-1 · 6절, 템플릿 넷, 종류 넷(대상 · 서술 · 사건 · 대장), 참고 블록과 표지 셋, 링크 세 꼴, 줄표 금지, 「…한다」 체, E_FORMAT 다섯. 새 E_FORMAT 은 만들지 않는다.
- 계약은 종류마다 하나다. 데이터는 `core/forms.js` 의 `FORMS` 한 벌에 둔다. 템플릿 글 · 프롬프트 블록 · 검사가 이 데이터에서 나온다. 갈래 장부(`_forms.md`)에는 지식마다 덮어쓸 「속성 정의」 블록만 더한다. 이 블록은 행 하나에 속성 하나를 적고, 칸 문자열로 몰지 않는다.
- 어디에 거는가
  - 새로 짓는 항목: Claude 짓기 길(들이기 · 바탕 세우기 · 다듬기 · 다시 그리기)에서 고쳐 받기를 한 번 하고, 남은 것은 알림이다.
  - 사람 편집 · 세션 저장: 새로 생긴 항목과 그 저장이 고친 줄에만 알림을 낸다(lintNew). 저장을 막지 않고 저장 승인 경고로 올리지도 않는다.
  - 옛 항목: 사람이 「짜임 맞추기」 를 골랐을 때만 건다.
  - 옛 기록(표지 `held` · `memo` · `migrate-held` · `## 넣지 못함`): 어떤 길에서도 다시 쓰지 않는다(P12).
- 원본 값과 문체: 원본에서 옮긴 표 칸 · 인용 · 값은 문체 규칙(noun-end 등) 밖이다. 글자를 바꾸지 않는다.

### 4-1. 문서 공통 뼈대

```
# <갈래 이름>            갈래 장부 이름 = 파일 이름
<요약 1~3문장: 이 문서가 무엇을 어떤 단위로 적나(「이슈 하나에 항목 하나」) + 문서 전체에 같은 값(사업명 · 용어 풀이)>
## <항목> …              종류 계약대로 · 차례는 ID · 날짜 · 원본 차례
<!-- kmd:참고 … -->      kmd 만 쓴다
```

- 요약에는 바뀌는 상태 · 수(「IS01 은 해결」)를 싣지 않는다. 그것은 항목 첫 문장이 정본이다. 요약 자리에 메타 · 표 · 목록 · 인용을 두지 않는다.
- 원본 파일에서 짓는 문서의 경우
  - 원본 메타(문서번호 · 판 · 작성 · 검토 · 승인 · 개정 이력 · 비밀구분)는 본문이 아니다.
  - 재료 처리(엑셀 일련번호를 바꿈 · 뺀 빈 열 · 끊긴 재료 · 원본 오타와 칸 밀림)도 본문이 아니다.
  - 이 둘은 참고 블록 `- (문서)` 아래 메모 줄에만 둔다(`글 출처:` · `개정 이력:` · `재료:`). 항목 키 아래에는 두지 않는다.
- kmd 에서 쓰는 설계서의 경우: 판 · 상태 · 근거는 「개요」 항목의 정의 목록에 둔다. 개정 줄은 경위이므로 기록이 지닌다. 장 번호를 걷을 때는 옛 번호와 항목의 짝표를 `- (문서)` 메모에 남긴다.
- 양식 시트(표지 · 개정이력표 · 작성지침 · 해더 · 목록 시트 · 필드 구조)는 항목으로 짓지 않는다.
  - 작성지침은 갈래 「속성 정의」 고칠 거리로 사람에게 알림을 낸다.
  - 목록 시트는 항목 머리와 요약이 된다.
  - 목록 시트에만 있고 본문이 없는 ID 는 항목을 세우지 않는다. 요약에 수와 ID 를 적는다.

### 4-2. 항목 공통

- 머리
  - 머리 꼴은 종류 계약을 따른다. 장 번호 · 링크 · 백틱만 있는 이름 · 문서 제목 되풀이는 넣지 않는다.
  - 옛 머리의 `값:` 앞부분은 장부 값이다. 지우거나 바꾸지 않고 장 번호만 뗀다(「설치: 3. 설치 순서」 → 「설치: 설치 순서」).
  - 머리 이름을 바꾸거나 항목을 나누는 일은 문서 짜임(지식관리자)만 한다.
- 첫 블록: 머리 다음 첫 블록은 1~2문장 문단이다. 대상 · 서술은 정의를 쓰고, 사건은 가장 큰 결과, 대장은 「무엇인 이슈이고 지금 상태(원본 값)」 를 쓴다. 메타 나열은 첫 문장이 아니다. 원본 값 이상이나 끊긴 재료 이야기를 첫 문장에 쓰지 않는다.
- 덩이 두 꼴
  - run-in 라벨 `- **라벨**: 내용` 은 사건 · 대장 · 결정에서 쓴다. 이름이 그 종류 계약의 라벨 목록에 있을 때만 라벨로 본다. 그 밖의 `- **x**: y` 는 정의 목록이고 라벨 검사 대상이 아니다.
  - 라벨이 여러 낱낱을 가지면 줄을 `- **라벨**:` 로 끝내고, 아래에 `*` 줄 하나에 하나씩 쓴다. 계약 라벨 아래는 낱낱이 하나여도 목록으로 쓴다(5-1 에 「계약 라벨 아래 `*` = 낱낱」 예외를 같은 커밋에서 더한다).
  - 수준 표시 `1.` · `1.1.` 은 대상 · 서술 · 절차 덩이와 긴 사건의 「다룬 것」 에 쓴다.
- 번호: 같은 부모 아래 같은 수준 번호는 1 → 2 → 3 으로 이어 센다. `1)` 은 덩이마다 1 부터 센다(5-1). 원본 단계 번호를 지켜야 하면 표의 「번호」 열에 값으로 둔다.
- 빈 값: 빈 값은 「-」 하나로 쓴다. 계약의 필수 라벨 · 필수 속성 행은 빼지 않는다.
- 지어내지 않기
  - 결정 · 할 일 · 상태 · 이름 · 날짜 · ID 꼴을 원본에 없는데 만들지 않는다.
  - 원본에 칸이 따로 없거나 「합의 · 결정 · 정함」 낱말이 없으면, 정한 것은 「원본에 따로 없음」 으로 둔다.
  - 이름이 없으면 머리는 ID 만 쓴다.
  - 칸 경계가 모호한 재료(슬라이드에서 평평하게 풀린 표)는 그 표를 짓지 않는다. 「칸 모호」 알림으로 사람에게 넘긴다.
- 끊긴 행 · 끊긴 문장은 옮기지 않는다.

### 4-3. 표 · 목록

- 고르기
  - 낱값 나열은 `-` 목록으로 쓴다.
  - 「이름: 설명」 짝은 정의 목록으로 쓴다.
  - 셋 이상 속성일 때 표로 쓴다.
  - 원본 표를 목록으로 바꾸는 일은 짓기(원본 재료)에서만 한다. 지금 지식을 다시 쓸 때는 하지 않는다(5-1 에 길마다 범위를 적는다).
- 첫 열은 행을 가리키는 값으로 둔다. 행 차례는 원본 차례다. 병합 머리는 풀어 열 이름 한 줄로 쓴다.
- 「〃」 · 「위와 같음」 대신 값을 되풀이한다. 표를 덩이로 나눌 때는 첫 행에 이어진 값을 다시 적는다.
- 열은 일곱까지 둔다. 넘으면 첫 열을 같이 두고 나누고, 원본 묶음 머리를 열 이름 접두로 붙인다(「환산 진도율 계획」). 어느 묶음인지 모호한 열은 첫 표에 두고 알림을 낸다. 두 값을 한 칸에 합쳐 열을 줄이지 않는다.
- 모든 행이 빈 열은 뺀다. 뺀 열 이름은 `- (문서)` 메모에 남긴다.
- 값 칸과 문장 칸
  - 값 칸(대장 속성 · 코드 표)은 값 하나로 쓴다.
  - 문장 칸(시험 수행 절차 · 예상 결과)은 길이 규칙 밖이다.
  - 셈에서 백틱 · 링크 · 괄호 안은 뺀다.
- 표 하나는 100행까지 둔다. 넘으면 대상(코드구분 · 시나리오)마다 항목을 나눈다. 한 대상의 값 목록은 한 표로 둔다.
- 목록은 2~7개가 좋다. 넘어도 알림만 낸다. 「등」 으로 끝내지 않는다.

### 4-4. 값

- 날짜는 YYYY-MM-DD, 시각은 「YYYY-MM-DD HH:MM」 으로 쓴다.
- 엑셀 일련번호와 부동소수 꼬리는 재료 변환(전처리)이 바꾸고, 원본 값을 `재료:` 메모에 남긴다. 값 대조는 전처리 뒤 재료를 근거로 삼는다.
- 원본 오타(「2202-08-26」 · 「잔행」) · 허용 밖 값(진행상태 「해결」) · 칸 밀림은 고치지 않는다. 알림으로 사람에게 넘긴다.
- 닫힌값은 작성지침이 아니라 실제 데이터에서 본 값 집합으로 정한다. 사람이 장부에서 넓힌다.

### 4-5. 한 사실 한 곳 · 링크

- 정본: 이슈 · 위험 · 요청의 내용과 상태는 대장에 둔다. 결정은 결정 항목, 정의는 대상 항목이 정본이다.
- 링크
  - ID 를 링크로 쓰는 것은 같은 지식의 항목 장부 · 문서 장부로 경로를 찾은 ID 뿐이다. 찾지 못하면 원본 글 그대로 둔다.
  - ID 꼴을 늘리거나 고치지 않는다(ISS-09 를 DPMS-ISS-09 로 만들지 않는다). 꼴이 다른 ID(IS1 · IS01)는 잇지 않는다.
  - 다른 원본의 값을 다른 문서 항목에 옮겨 넣지 않는다.
- 정례 보고의 누적 표는 그때의 사실이다. 그 종류의 대장이 같은 지식에 있을 때만 「상태 한 마디 + 링크」 로 줄인다. 없으면 표를 그대로 둔다.
- 같은 문서의 장 번호 참조(「4절」 · 「6.3」)는 그 장이 항목으로 있으면 항목 링크로 바꾼다. 다른 문서의 장 번호는 그대로 둔다.

### 4-6. 종류별 계약(갈래 뼈대)

각 계약은 다섯 가지를 정한다: 물음 · 머리 · 첫 문장 · 속성 · 라벨(덩이) 차례 · 깊이. 표시는 `!` 필수, `?` 선택이다.

#### 대상(지식문서 서식)
- 물음: 이것이 무엇이고 값이 무엇인가.
- 머리: 「ID: 이름」 또는 「이름」. ID 가 겹치는 대상(BD001 · SY003)은 머리를 「이름」 으로 가르고 dup-id 를 막음으로 다룬다.
- 차례: 첫 문장 ! → 속성 표 또는 정의 목록 ? → 값 표 ? → `1.` 덩이 ?(라벨 자유 · 깊이 2) → 관련 줄 ?
- 절차 덩이(대상 안 쓰는 법)
  - 라벨: 준비 ? · 단계 ! · 확인 ? · 마친 뒤 ? · 되돌리기 ? · 주의 ?. 맞는 라벨이 없으면 원본 소제목을 그대로 쓴다.
  - 단계 줄 `1)` 은 한 줄에 동작 하나다. 어디서 · 조건을 앞에, 결과는 뒤 문장에 쓴다. 한 덩이에 열 개를 넘으면 알림을 낸다.
- 시험 항목
  - 첫 문장 다음 속성 줄 꼴: `- **사전 조건**:` · `- **사후 조건**:` · `- **관련 프로세스 ID**:` · `- **관련 요구사항 ID**:` · `- **테스트 결과**:`. 양식 자리표시(「PASS/FAIL」)는 「-」 로 쓴다.
  - 덩이 이름은 원본 `*` 흐름 표시에서만 가져온다.
  - 단계 표 `| 번호 | 화면 | 수행 절차 | 테스트 데이터 | 예상 결과 |`. 번호는 원본 No. 그대로, 화면 칸은 값을 다 적는다.

예:
```
## HR001: 직급

직급 코드는 10개다.

| 코드 | 코드명 | 연관1 |
|---|---|---|
| `0001` | 대표이사 | 노무비 |
| `0002` | 이사 | - |
```

#### 서술(지식문서 서식)
- 물음: 무엇을 정했고 왜인가.
- 머리: 주제 이름(옛 `값:` 은 지킨다).
- 차례: 첫 문장(결론) ! → `1.` 덩이(깊이 2) → 관련 줄. 절차가 다섯 줄을 넘으면 대상의 절차 덩이로 떼고 링크한다.

#### 사건(작업기록 서식 · 지금 템플릿 라벨을 지키고 더하기만 한다)
- 물음: 무엇을 정했고 누가 무엇을 하나.
- 머리: 「YYYY-MM-DD 주제」. 주제는 원본 회의명이다. 정례 보고는 「YYYY-MM-DD N주차」 를 쓰고, 날짜가 원본에 없으면 「N주차」 로 둔다(알림만 · 날짜를 지어내지 않는다 · 작성기준 6 · 6-1 을 같은 커밋에서 고친다).
- 차례
  1. 첫 문장 !
  2. `- **누가**:` ! 소속 이름 · 이름, 소속 이름(진행 · 작성: 이름)
  3. `- **때 · 곳**:` ?
  4. `- **안건**:` ?
  5. `- **무엇을**:` ?(3~6줄)
  6. `- **정한 것**:` !
  7. `- **남은 것**:` !
  8. 긴 회의는 결과 라벨 뒤에 `1. 주제` · `1.1.` 덩이(무엇을 대신)
- 정한 것 · 남은 것: 원본에 결정 · Action 칸이나 합의 낱말이 있을 때만 채운다. 없으면 「원본에 따로 없음」 이고, 비면 「없음」 이다.
- 남은 것 줄 꼴: `* <할 일>: <맡은 이> · 기한 <YYYY-MM-DD|->`. 할 일이 앞이고 맡은 이가 뒤다.
- 오래 갈 결정은 결정 항목이 정본이고, 사건에는 링크를 둔다.
- 정례 보고: 덧 덩이 차례를 갈래 장부 「속성 정의」 에 둔다(금주 주요 이슈 활동 · 공정 진도 · 업무 추진 · 단위 프로그램 개발 · 주요 일정 · 요청 및 협의 · 이슈 · 결심 · 변경 · 위험).

예:
```
## 2022-08-30 실무자 인터뷰

공무팀 실무자를 인터뷰해 AS-IS 업무와 TO-BE 요구를 모았다.

- **누가**: 나라기업 전성진 · 김지현, 세정아이앤씨 박재성 · 사경진 (진행 · 작성: 박재성)
- **때 · 곳**: 2022-08-30 10:00 · 나라기업 김해 오피스
- **안건**: 업무 분석 및 요구사항 수집
- **정한 것**:
* 원본에 따로 없음
- **남은 것**:
* 수기 관리 엑셀 파일 전달: 김지현 · 기한 -
* 자금일보 대체금액 항목 확인: 김지현 · 기한 -

1. 공무팀 업무 분석
1.1. 보고
- 공사 진행사항 · 소요 · 인원을 주 단위로 보고한다.
```

#### 대장(결정기록 서식 · 속성은 갈래 「속성 정의」)
- 물음: 지금 상태는 무엇이고 누가 언제까지 하나.
- 머리: 「ID: 이름」. 이름이 없으면 「ID」 만 쓴다.
- 원본 ID 행마다 항목 하나를 세운다. 빈 행은 머리 · 첫 문장 · 속성 표(모두 「-」)로 두고 라벨은 생략할 수 있다. 빈 행이라는 사실은 알림(empty-row)으로만 남긴다.
- 차례: 첫 문장 ! → 속성 표 `| 속성 | 값 |` ! → `- **내용**:` ! · `- **해결방안**:` ! · `- **협조**:` ? · `- **결과**:` ! (+ 지식이 덮어쓴 라벨, 예 DPMS 「결론(지금)」 · 「정본」)
- 속성 표: 행 이름과 차례는 속성 정의를 따른다. 값 칸에는 값 하나와 날짜까지만 쓰고, 문장은 라벨로 보낸다.

속성 정의 예(갈래 장부 블록 · 원본 작성지침에서):

| 속성 | 원본 칸 | 쓰는 법 | 필수 |
|---|---|---|---|
| 유형 | 이슈 유형 | 범위 · 일정 · 인력 · 비용 · 품질 · 기술 · 기능 · 장비 · 정책 | ! |
| 식별단계 | 이슈식별단계 | 착수/계획 · 분석 · 설계 · 구축 · 시험 | ! |
| 발생일 | 이슈 발생일 | 날짜 | ! |
| 제기 | 이슈 제기자 | 이름 | ? |
| 긴급도 | 긴급성 | 상 · 중 · 하 | ? |
| 진행상태 | 해결여부 | 데이터에서 본 값(식별 · 진행중 · 종료 · 해결) | ! |
| 해결일 | 이슈 해결일 | 날짜 | ! |

#### 결정(결정기록 서식)
- 차례: 정한 것 ! · 까닭 ! · 버린 안 ?(`* 안: 까닭`) · 상태 !(유효 | 보류 | 대체됨: [새 결정](#머리)) · 영향 ? · 정한 때 ? · 사람 ?

#### 기록(work/ · 새 기록만)
- 머리말과 제목은 kmd 가 쓴다. 요약은 한 문단 300자 안이다.
- 칸 차례: 바뀐 것 · 까닭 · 버린 안 · 영향 · 근거.
- recordBody 가 칸을 `- x` 줄로 다시 엮으므로 줄 꼴은 한 줄이다. 덧말 `*` 은 쓰지 않고 괄호에 둔다.
- 바뀐 것: `대상: 옛 → 새` · `새로: 대상 값` · `뺌: 대상`. 쌍점은 한 번만 쓴다.
- 버린 안: `안: 까닭`. 근거: `종류: 값`.

### 4-7. 기계 검사

수준은 셋이다. 「고쳐 받기」 는 짓기 길에서 돌려 보내고 남으면 알림으로 둔다. 「알림」 은 짜임 알림이다. 「제안」 은 약한 알림이다. 막는 검사는 지금 E_FORMAT 다섯뿐이다.

1단계에 켜는 확정 검사(고쳐 받기):
- no-summary: `# 제목` 다음이 문단이 아니거나 네 문장이 넘는다.
- no-lead: `##` 다음 첫 블록이 표 · 목록 · 라벨 · 덩이다(applied 표지 뒤).
- head-form: 종류 정규식에 맞지 않는다. 사건 `^\d{4}-\d{2}-\d{2} .+$` 또는 `^(\d{4}-\d{2}-\d{2} )?\d+주차$`, 대장 `^[A-Za-z][\w-]*\d+(: .+)?$`. 머리 장 번호는 `(^|: )\d+(\.\d+)*\.? ` 로 잡는다. 날짜 없는 주차는 알림만이다.
- head-value: 옛 머리의 `값:` 이 바뀌거나 사라졌다(막음급 알림 · 짓기 거절 후 고쳐 받기).
- form-meta: 머리가 표지 · 개정이력 · 작성지침 · 해더 · 양식 · 필드 구조다.
- id-rows: 원본 표 ID 집합이 지은 머리 ID 집합에 다 들어 있지 않다(짓기만).
- num-repeat: 같은 부모 · 같은 수준 번호가 되풀이되거나 건너뛴다(자동 고침 가능).
- table-cols: 표 줄 칸 수가 머리와 다르다(지금 검사).
- missing-label: 계약 필수 라벨이 없다(새 항목만).
- prop-rows: 대장 속성 행이 빠졌거나 차례가 다르다(새 항목만).
- date-mismatch: 사건 머리 날짜와 「때 · 곳」 날짜가 다르다.
- raw-date: 날짜 칸에 4~5자리 정수 · 「2022. 08.30」 꼴이 있다(전처리가 바꾸고, 남으면 고쳐 받기).
- ref-key: 참고 블록 항목 키가 문서 머리 전체 글과 맞지 않는다(withRef 가 걷을 줄).
- cut-line: 줄이 문장 부호 · 칸 끝으로 닫히지 않았다(끊긴 재료).

알림:
- unknown-label: 계약 목록에 있는 라벨이 두 번 나오거나 차례가 다르다(목록 밖 굵은 줄은 정의 목록으로 보고 넘긴다).
- todo-form: 남은 것 `*` 줄이 `^\* .+: .+ · 기한 (\d{4}-\d{2}-\d{2}|-)$` 꼴이 아니다.
- cell-list: 값 칸 하나에 「 · 」 · 「, 」 조각이 다섯 이상이다(백틱 · 링크 · 괄호 안 제외 · 표 칸만).
- cell-long: 대장 속성 값 칸이 60자를 넘거나 문장 둘 이상이다(백틱 제외).
- wide-table: 열이 여덟 이상이다.
- col-group: 표를 나눌 때 묶음이 모호한 열이 있다.
- ditto: 칸이 「〃」 · 「위와 같음」 이다.
- empty-col: 모든 행이 빈 열이다(짓기는 자동으로 빼고 메모).
- empty-row: 대장 항목 값이 모두 「-」 다.
- bad-value: 닫힌값 밖이거나 연도가 1990~2100 밖이다(원본은 바꾸지 않는다).
- dup-id: 같은 문서에서 머리 ID 가 겹친다.
- id-link: 장부로 경로를 찾은 ID 가 링크 밖에 있다.
- id-near: 0 채움 · 대소문자만 다른 ID 가 있다(잇지 않는다).
- sec-ref: 같은 문서 장 번호 참조가 남았다.
- source-drift: 원본에서 옮긴 칸 글이 원본 재료와 글자로 다르다(짓기만).
- meta-lump: 한 문단에 「X: … Y: … Z: …」 가 셋 이상이다.
- step-chain: 「→」 로 이은 동작이 셋 이상이거나, 한 덩이에 `1)` 이 열 개를 넘는다.
- status-link: 결정 「대체됨」 에 링크가 없다.
- rec-change-form: 새 기록 바뀐 것 줄 꼴이 어긋났다.

제안(재 본 뒤 올림):
- noun-end: 문단 · 목록 끝이 (불가|예정|필요|완료|진행)\. 이다(원본 칸 · 표 · 라벨 값 제외).
- list-shape: 목록이 여덟 이상이거나 「등」 으로 끝난다.
- dup-fact: 40자 넘는 같은 문장이 있다(대상 · 서술만 · 정례 누적 표와 시험 단계 제외).
- history-in-body: 본문에 날짜와 개정 줄이 다섯 이상이다.

빼는 것:
- multi-target: 기계 검사에서 뺀다. 대상 하나의 이름에 「·」 가 드는 경우와 가를 수 없다.

### 4-8. 프롬프트 꼴

`WRITE_RULES` 뒤에 짓는 갈래의 계약 블록 하나만 붙인다. 블록은 FORMS 와 속성 정의에서 만든다.

```
이 갈래 서식(위험및이슈관리대장 · 대장):
- 물음: 지금 상태와 누가 언제까지 하나.
- 문서: # 제목 다음 요약 1~3문장(무엇을 · 단위). 상태 · 수는 요약에 쓰지 않는다.
- 머리: 「ID: 이름」, 이름이 없으면 ID 만. 원본 ID 행마다 항목 하나(빈 행 포함).
- 차례: 첫 문장(무엇인 이슈 · 원본 상태) → | 속성 | 값 | → - **내용**: → - **해결방안**: → - **협조**: → - **결과**:
- 속성 행(이 차례 · 빠짐 없이 · 빈 값 「-」): 유형 · 영역 · 식별단계 · 발생일 · 제기 · 관리범위 · 중요도 · 긴급도 · 처리 담당 · 등록일 · 완료 예정일 · 진행상태 · 해결일
- 지키기: 원본 값 · 칸 글은 글자 그대로. 결정 · 상태 · 이름 · ID 를 지어내지 않는다. 다른 원본 값을 옮겨 오지 않는다. 장부에서 경로를 모르는 ID 는 링크하지 않는다. 원본 오타 · 빈 칸 · 끊김은 본문에 쓰지 않는다(kmd 가 메모).
- 좋은 예: <FORMS.good 한 덩이>
- 나쁜 예: <FORMS.bad 한 덩이 · 예: 메타를 한 문단에 몰기 · 1. 1. 1. 번호>
```

고쳐 받기 꼴(같은 세션 · 한 번):
```
서식 검사에 걸린 줄이다. 이 줄만 고쳐 다시 내라. 값은 바꾸지 않는다.
- <검사 id> <머리> <줄 번호>: <걸린 글> → <규칙 한 줄>
```
